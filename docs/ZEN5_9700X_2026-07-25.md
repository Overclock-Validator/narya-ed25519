# Zen 5 measurements — Ryzen 7 9700X, 2026-07-25

narya's first Zen 5 data. Every prior number is Zen 4 (8700GE), which double-pumps
512-bit operations as 2x256; Zen 5 has a native 512-bit datapath, so the two are
not interchangeable and several conclusions below do not transfer.

## Environment

| | |
|---|---|
| CPU | AMD Ryzen 7 9700X, Zen 5, 8 physical cores / 16 threads |
| Memory | 59 GB |
| AVX-512 | f, vl, dq, bw, **ifma**, vbmi, vbmi2, bitalg, vnni, bf16, vp2intersect |
| Go | 1.26.4 linux/amd64 (matches the version pinned for 8700GE gates) |
| Pinning | `taskset` to physical cores 0..N-1 (CPUs 8-15 are SMT siblings) |
| Commit | c89ae07 plus the promotion commits on `claude/narya-perf` |

All rows below are zero-allocation (`0 B/op`, `0 allocs/op`) unless stated.

## 1. Single signature, default (generic) backend

Pure Go, no IFMA — this is what `pick("")` selects.

| impl | msg=200 | sig/s/core |
|---|---:|---:|
| `crypto/ed25519` | 26,481 ns | 37,763 |
| narya compat | 25,767 ns | 38,809 |
| narya strict | 25,786 ns | 38,780 |
| narya cached (generic comb) | 11,526 ns | 86,760 |

narya's **strict** path is 2.6% faster than stdlib while performing strictly more
work (small-order rejection on both A and R). The same holds on arm64 (M4 Pro),
so it is not an artifact of one microarchitecture.

## 2. Registered r51 IFMA backend, public API

`SetBackend("r51")` + `VerifyBatchStrict`, single core.

| n | msg=200 | vs stdlib |
|---:|---:|---:|
| 1 | 21.94 us | 1.21x |
| 4 | 12.79 us | 2.07x |
| 8 | 12.39 us | 2.14x |
| 64 | 12.03 us | 2.20x |

n=1 pays for four lanes and uses one. Saturated by n=4.

## 3. Multicore scaling

`BenchmarkR51IFMABatchQParallel`, n=64, msg=200.

| finalizer | 1 core | 4 cores | efficiency |
|---|---:|---:|---:|
| paired-AR-projective | 81,079 sig/s | 318,493 sig/s | 98% |
| single-A-batch-Q | 84,899 sig/s | 331,997 sig/s | 98% |

At msg=1232, 1 -> 6 cores holds 93-95% across stdlib, two-x4 and x8. Zero
allocations means no GC pressure and tables are shared read-only, which is why
efficiency is far above the usual 80-85%.

`single-A-batch-Q` beats `paired-AR-projective` by 4-5% at both core counts.

## 4. Pipeline shortlist — the two-x4 / x8 crossover

**This is the most important result here.** msg=1232, 1 core, radixA=32/comb256.

| n | two-x4 | x8 | winner |
|---:|---:|---:|---|
| 4 | 12.50 us | 17.68 us | two-x4 by 41% |
| 8 | 12.47 us | **9.24 us** | x8 by 26% |
| 16 | 12.50 us | 9.30 us | x8 by 26% |
| 32 | 12.51 us | 9.31 us | x8 by 26% |
| 64 | 12.53 us | 9.46 us | x8 by 25% |
| stdlib | 27.5 us | | |

two-x4 is flat across a 16x range in n. x8 is flat from n=8 onward and collapses
only at n=4, where it fills half its lanes and pays for all of them. The crossover
is a **step, not a curve**: the dispatch rule is simply `n >= 8 -> x8`.

x8 at n>=8 is **2.97x stdlib**.

Full ranking at n=64, msg=1232:

| config | us/sig | vs stdlib |
|---|---:|---:|
| x8 / radixA=32 / comb256 | 9.33 | 2.94x |
| x8 / radixA=64 / shared | 9.84 | 2.79x |
| x8 / radixA=16 / shared | 10.95 | 2.51x |
| two-x4 / radixA=32 / comb256 | 12.53 | 2.19x |
| **two-x4 / radixA=64 / shared** (registered) | 13.32 | 2.06x |
| two-x4 / radixA=16 / shared | 14.79 | 1.86x |

`two-x4 / radixA=32 / comb256` beats the registered `radixA=64 / shared` at BOTH
n=4 (12.50 vs 13.35) and n=64 (12.53 vs 13.32) — about 6% either way, same
pipeline kind, no dispatch needed.

CAUTION: none of this transfers to Zen 4 unmeasured. Zen 4's double-pumping is
the likely reason two-x4 was chosen originally, and the x8 advantage may shrink
or invert there.

## 5. Warm partial comb (A6r9-B10r5)

Parallel matrix, distinct keys.

| n | msg | 1 core | 6 cores | scaling |
|---:|---|---:|---:|---:|
| 4 | 200 | 4.38 us / 228,279 sig/s | 0.775 us / 1,289,915 sig/s | 94% |
| 4 | 1232 | 5.13 us / 194,950 sig/s | 0.916 us / 1,091,202 sig/s | 93% |
| 64 | 200 | 3.71 us / 269,379 sig/s | 0.664 us / 1,506,975 sig/s | |
| 64 | 1232 | 4.49 us / 222,861 sig/s | 0.801 us / 1,248,029 sig/s | |

Over 1.2M sig/s on six cores at max transaction size, 6.1x stdlib per core.

**These are a 100% cache-hit ceiling, not a steady state.** Tables are prepared
outside the timed region. Real throughput blends this with the cold path at
whatever the actual key-recurrence rate is.

Key diversity is irrelevant to the timed loop (distinct-keys 4.437, four-key-cycle
4.403, same-key 4.444 at n=4/msg=200) because preparation is excluded.

## 6. Cache economics

| quantity | value |
|---|---|
| A6/r9 table size | 19,200 B/key (43 digits, 5 rows, 32 entries) |
| keys at 128 MiB | 7,158 |
| build, vectorised x4 | 13,053 ns/key (52.2 us per x4 group) |
| build, scalar | 2,411,108 ns/key — 185x slower, unusable |
| saving per warm verify | 12.03 - 3.73 = 8.30 us (msg=200, n=64) |
| **break-even** | **13.05 / 8.30 = 1.6 verifies** |

A key pays for its table the **second** time it is seen. This is the number that
justifies the cache, and it argues the planned `AdmitAfter=8` is far too
conservative — 2 is closer to right.

The 7,158-key limit is simply budget / table size, not an arbitrary cap. Narrowing
the comb trades online work for capacity:

| spec | rows | entries/row | bytes/key | keys @128 MiB |
|---|---:|---:|---:|---:|
| A6/r9 (current) | 5 | 32 | 19,200 | 7,158 |
| A5/r9 | 6 | 16 | 11,520 | 11,930 |
| A4/r9 | 8 | 8 | 7,680 | 17,895 |

CAVEAT: a single-key build still costs the full 52.2 us group operation, because
the 13.05 us/key figure comes from sharing one inversion across four lanes.
Building keys one at a time moves break-even from 1.6 to 6.3 verifies. Admissions
should be batched four at a time to keep the cheaper figure.

## 7. Structural constraints found while integrating

Recorded because they shape the backend design, not because they are performance
numbers:

- The warm comb **cannot verify fewer than 4**: the constructor requires a
  positive multiple of `X4Lanes`. So the singleton `backend.verify` path can never
  use a cached table; only batches can.
- A warm group must be **homogeneous** — all four lanes prepared. There is no
  mixed warm/cold group, so a group with three hits and one miss falls entirely to
  the cold path. With diverse fee-payers this wastes most cache hits.
- Message size costs the warm path more in relative terms (+21% from 200 to 1232)
  than the cold path (+6%), because SHA-512 is a larger fraction of a 4.5 us
  verify than of a 12 us one. **Hashing matters more as point arithmetic gets
  faster**, which strengthens the case for the multi-buffer SHA-512 work.

## Reproducing

```
GOMAXPROCS=<n> taskset -c 0-<n-1> go test -run '^$' \
    -bench BenchmarkR51IFMAPipelineParallel -benchtime 1s ./ed25519/
GOMAXPROCS=<n> taskset -c 0-<n-1> go test -run '^$' \
    -bench BenchmarkWarmCombParallelMatrix -benchtime 3s ./internal/r51x5/
```

1s and 3s benchtimes agree within 0.4% on this machine; 1s is enough for the
pipeline sweep.
