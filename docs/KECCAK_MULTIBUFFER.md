# Multi-buffer Keccak

`keccakmb` runs eight independent Keccak-f[1600] permutations at once, one per
64-bit lane of the AVX-512 ZMM registers, and builds the Keccak sponges on top.
It produces exactly the output of `crypto/sha3` for SHA3-256, SHAKE128 and
SHAKE256, and of legacy Keccak-256 (padding byte `0x01`) as used by Ethereum,
`sol_keccak256` and the secp256k1 precompile.

No verifier in this module calls it yet. The consumers in view are:

- Falcon (FN-DSA) verification, whose hash-to-point step squeezes about
  1.1 KB of SHAKE256 per signature. `SpongeX8` squeezes one block per lane at
  a time for that rejection-sampling loop;
- the secp256k1 precompile, which hashes the message and the recovered public
  key with legacy Keccak-256;
- the `sol_keccak256` syscall.

It only helps when there are several independent messages to hash. A single
message still pays for a full eight-lane permutation (about 321 ns on Zen 4),
which is slower than a scalar implementation.

## Surface

Like `sha512mb`, the plain entry points (`Sum`, `SumBatch`,
`PermuteX8Generic`, `NewSpongeX8Generic`) are the portable reference and never
dispatch. The kernels are reached only through `ExperimentalPermuteX8`,
`ExperimentalSumBatch` and `ExperimentalNewSpongeX8`, which return false when
AVX-512F is unavailable. Batches may mix message lengths and pass each message
in several parts.

Both batch entry points accept `out[i]` sharing storage with `msgs[i]`
(in-place hashing), but not with any other lane's message: the scalar loop
writes lane 0 before reading lane 1, while the kernel absorbs a whole group of
eight first, so cross-lane overlap is documented as unsupported. Message
lengths are summed with overflow checks, because parts may alias one buffer
and exceed the `int` range on 32-bit Go. `SqueezeBlock` writes only
`out[j][:rate]` for absorbed lanes on both paths; the scatter kernel masks
the other lanes.

## Kernels

`keccakmb/native_amd64.s` is generated by `scripts/gen_keccakmb_amd64.py`,
which derives the pi lane cycle and rotation offsets from the FIPS 202
definitions. It has three functions that share one permutation body.

**Permutation.** The 25-word state of all eight instances stays in Z0 to Z24
for all 24 rounds.

- theta: two XORs and one three-way `VPTERNLOGQ` per column parity (Z25 to
  Z29), then one `VPROLQ` and five three-way `VPTERNLOGQ` per column.
- rho and pi: pi moves the 24 non-origin lanes around a single 24-cycle. The
  kernel walks that cycle backwards with one saved register (Z30), so each
  destination is written after its old value was read and every round starts
  with the same register assignment. That costs 24 `VPROLQ` and one move.
- chi: `VPTERNLOGQ` with immediate `0xd2` computes `a ^ (~b & c)`, with Z25
  and Z26 (dead after theta) holding each row's wrap-around terms.
- iota: one broadcast and one XOR.

That is about 105 instructions per round for eight permutations. Z31 is never
touched by the permutation.

**Absorb** (`absorbX8Native`). Z31 holds one block pointer per lane. Each
block is XORed in with 17 (rate 136) or 21 (rate 168) `VPGATHERQQ` loads,
rotated over Z25 to Z30 and zeroed first so consecutive gathers do not
serialize on a merged destination, then permuted, and the pointers advance by
a per-lane stride. One call covers as many blocks as every active lane can
read in place from a single contiguous segment. A block that crosses a
segment boundary, and every padded final block, is staged into a per-lane
buffer and absorbed in a one-block call. Lanes that are absent or already
finished read a zero block, and their saved states are restored afterwards.
The advanced pointers live only in Z31 and are never written back to Go
memory. When every message is a single block, the Go XOR loop is used
instead, because it measured faster for that case.

**Squeeze** (`squeezeX8Native`). Optionally permutes, then writes each output
block with masked `VPSCATTERQQ` stores straight into the absorbed lanes of a
`[8][200]byte` buffer. Digests that fit in the first block skip both and copy
only the words they need.

## Correctness evidence

- The reference permutation matches the published Keccak-f[1600] output for
  the all-zero state, and the reference sponge matches the published legacy
  Keccak-256 digests of `""` and `"abc"`.
- The reference sponge matches `crypto/sha3` for SHA3-256, SHAKE128 and
  SHAKE256 with 1,100-byte squeezes, at every length within two bytes of one,
  two and three blocks of both rates, plus short and long messages, split into
  three parts.
- Both x8 permutations match the reference on 200 states per run, half of them
  with lanes that differ in one bit, to catch leakage between lanes.
- Mixed-length batches of 1 to 17 messages, each split into up to five parts at
  random points, for all four variants with random SHAKE output lengths, match
  the reference and `crypto/sha3` (40 batches per variant and size).
- Block-by-block SHAKE256 squeezing over a 40-byte nonce plus message matches
  the `crypto/sha3` reader for ten blocks.
- `FuzzSumBatch` compares the native batch with the reference. One minute on
  the Zen 4 machine (about 0.94M executions) found nothing, before and after
  the absorb and squeeze kernels.
- Legacy Keccak-256 from the native batch matches `golang.org/x/crypto/sha3`
  (`NewLegacyKeccak256`, the implementation geth uses) at 32, 64, 136, 532 and
  1,232 bytes.
- CI runs the native tests and the fuzz seeds under Intel SDE, and
  `TestSDENativeKeccakRequired` fails the job if the emulated CPU lacks
  AVX-512.

## Performance

Ryzen 7 PRO 8700GE (Zen 4), Go 1.27.2, one pinned core, five 1-second runs per
row on an otherwise idle machine; the spread across runs was under 4% for
every row. Each operation processes eight messages; divide by eight for the
time per hash.

| Work per operation | `crypto/sha3` | permutation kernel, Go absorb and squeeze | `ExperimentalSumBatch` |
| --- | ---: | ---: | ---: |
| SHA3-256, 64-byte messages | 2,095 ns | 619 ns | 645 ns (3.2x) |
| SHA3-256, 1,232-byte messages | 17,260 ns | 4,995 ns | 3,795 ns (4.5x) |
| SHAKE256, 104 bytes in, 1,088 out (Falcon-size) | 13,590 ns | 3,480 to 3,600 ns | 3,500 to 3,630 ns (3.8x) |
| SHAKE256, 1,272 bytes in, 1,088 out | 28,800 ns | 7,840 ns | 6,656 ns (4.3x) |
| 8 bare permutations | 18,630 ns (portable reference) | 321 ns | |

The middle column runs the same permutation kernel with the Go absorb and
squeeze loops, so it isolates what the other kernels add:

- The gather absorb saves about 1.2 us per eight 1,232-byte messages (24%).
- The scatter squeeze shows no measurable gain over the Go loop at Falcon's
  output size; the two SHAKE256 104-byte columns are within noise.
- Batches whose messages are all single blocks take the Go loop, because the
  gather absorb measured slower there (about 700 ns). Through
  `ExperimentalSumBatch` that case still costs about 4% more than calling the
  loop directly (645 against 619 ns), which is the batch entry point's own
  overhead.

An earlier version stored the permutation as a function value in
`SpongeX8`, which made every batch call heap-allocate its sponge; the
numbers above are after that fix.

Legacy Keccak-256 against `golang.org/x/crypto/sha3`, hashing the same eight
messages one at a time with a reused hasher as geth does:

| Message | `x/crypto` | `keccakmb` x8 | Speedup |
| --- | ---: | ---: | ---: |
| 32 bytes (storage-slot key) | 1,928 ns | 640 ns | 3.0x |
| 64 bytes | 1,939 ns | 639 ns | 3.0x |
| 136 bytes (two blocks) | 3,755 ns | 976 ns | 3.8x |
| 532 bytes (full trie branch node) | 7,557 ns | 1,707 ns | 4.4x |
| 1,232 bytes | 18,731 ns | 3,793 ns | 4.9x |

The kernel costs about 40 ns per permutation against roughly 215 ns for
`crypto/sha3`. Not measured yet: an AVX2 x4 kernel for machines without
AVX-512, Zen 5, and reth's `keccak-asm`.

## Related work

The lane-per-instance layout is the standard way to run several Keccak
instances in SIMD registers; XKCP's `KeccakP-1600-times8` is the reference
example. Firedancer also has an experimental eight-lane AVX-512 Keccak,
`fd_keccak256_core_8` in `src/ballet/falcon/fd_keccak8x.h` on its
`drubin/falcon-experiments` branch (commit 4b4141ddb6, April 2026), with the
same one-instance-per-lane layout. It runs 12 rounds as part of an experimental
parallel XOF for Falcon hash-to-point, so it is not standard Keccak-f[1600] or
SHAKE256. `keccakmb` was written independently of it: its register
allocation, in-place rho and pi chain, gather absorb and scatter squeeze are
our own, and it computes the standard 24-round functions.
