# Zen 4 r51 checkpoint — Ryzen 7 PRO 8700GE

This note records the experimental state derived from Narya commit
`aa483fad49ef18e3947b850e3c73e83dd90cb288`.  The r51 work described here is
forced-test-only: it is not registered for production dispatch.

## Environment

- CPU: AMD Ryzen 7 PRO 8700GE (Zen 4)
- OS: Linux/amd64
- Go: 1.26.4
- Primitive and single-worker measurements: one pinned physical core,
  `GOMAXPROCS=1`
- Correctness: full package suite on both the development host and the Ryzen

Long benchmark runs occasionally entered an approximately 2x slower frequency
or host-load state even though the governor reported `performance` and cgroup
throttling remained zero.  Release comparisons must therefore use interleaved
A/B candidates under the same toolchain, with an explicit warm-up and several
short samples.  The absolute values below are representative stable clusters,
not release claims by themselves.

## Correctness status

The following all pass:

- the complete Go test suite;
- CCTV and Wycheproof vectors;
- strict encoding edges, all small-order aliases, and mixed-order points;
- every x4/x8 invalid-lane position and fail-closed injected errors;
- generic, stdlib, r51, and Oasis differential tests;
- 512 deterministic honest and mutated Oasis-versus-Narya rounds;
- zero-allocation gates for ordinary r51, comb, admitted/fallback HEEA, and
  the x4/Oasis-tail dispatcher;
- assembly range, aliasing, maximum-limb, and conditional-negation tests.

The production arithmetic contract remains composable u52 inputs and proven
u61 folded products.  The parallel carry has not widened that public/internal
contract to arbitrary u64 limbs.

## Changes in this checkpoint

- one x4/x8 vector parallel carry replaces scalar per-lane normalization;
- vector add, subtract, and negate include their required carry/fold pass;
- concrete radix dispatch removes interface-driven hot-path heap escapes;
- fixed three-segment SHA-512 batching hashes the original `R || A || M`
  bytes without constructing `[][][]byte`;
- the canonical-S precheck is allocation-free;
- the test-only Oasis comparator uses the exact DalekStrict-compatible option
  set, including permissive decodable `A` and canonical `R`;
- a test-only dispatcher sends complete four-signature groups to r51 x4 and a
  one-to-three-signature tail to exact Oasis cold or expanded verification.

## Measured results

### Parallel carry, interleaved A/B

Complete x4 radix-64 verification improved by about 3–3.5%:

| batch | before (us/sig) | parallel carry (us/sig) | change |
| ---: | ---: | ---: | ---: |
| 4 | 20.30 | 19.59 | -3.5% |
| 8 | 20.26 | 19.62 | -3.1% |
| 64 | 20.43 | 19.71 | -3.5% |

### SIMD width

For 200-byte messages, stable pre-parallel-carry samples were approximately:

| path | n=8 (us/sig) | n=64 (us/sig) |
| --- | ---: | ---: |
| stdlib loop | 36.64 | 36.68 |
| r51 x8 | 21.24 | 21.30 |
| two r51 x4 groups | 20.47 | 20.53 |

Two x4 groups are about 3.6% faster than one x8 group on this Zen 4 CPU.  Zen
4 planning should therefore use x4 as the default experimental width and keep
x8 as an independently measured candidate, not an assumed win.

The width-aware design improves the cold one-signature case by roughly 30%
against a 36–37 us stdlib baseline and complete x4 groups by roughly 48–50%.
This is stronger evidence than a single hard batch-8/batch-64 gate for the
expected small-to-large workload distribution.

Oasis expanded-key construction is approximately 3.9 us and stores about
1.5 KiB.  Narya's generic full `PubkeyTable` already implements a 32-by-8
pre-shifted arbitrary-key comb using 30,720 bytes.  A future r51 hot-key table
must therefore be compared with both of these existing cache tiers rather than
treated as a new algorithm in isolation.

## Decisions and next experiments

1. Keep the vector parallel carry and the x4-first Zen 4 direction.
2. Fuse raw multiplication and the parallel carry into one assembly entry
   point.  Keep it only if complete x4 verification improves by at least 2%.
3. Prototype single-A decode plus native batch encoding of computed `Q` before
   attempting raw-`Q`/encoder fusion.  Compare the complete exact predicate
   against paired A/R decode at widths 1–17, 32, and 64.
4. Only then consider fused point add/double or a radix-64 scalar-loop
   superkernel.  Any older `DBL5+ADD` proposal must be adapted to the measured
   radix-64/x4 winner.
5. Treat raw-coordinate, carry-on-consume, and operand-resident multiplication
   as scheduling techniques inside those fused assembly kernels.  Do not
   expose a general Wide63/u64 field contract without a separate proof and
   differential boundary tests.
6. Evaluate a shared r51 hot-key comb first for shred/validator-key traffic,
   where all x4 lanes can naturally share `A`.  Use measured reuse distance and
   build amortization; do not infer it from the accounts cache.
